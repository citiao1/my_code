# PID 调参工具比较与优化交接

更新日期：2026-10-21（Asia/Shanghai）

## 目的

本文件交接 PID_Helper 与工作区现有 PID 调参适配器的比较结论，并说明如何提升实际参数搜索质量，以及如何完善 `pid-tuning` skill，便于后续继续处理。

## 结论摘要

- 若只比较参数搜索算法，PID_Helper 当前公开介绍的能力强于工作区适配器的角环候选生成器：它提供系统辨识初值、分阶段整定和 PSO；当前适配器主要按响应评分做有限规则调整。
- 这不等于 PID_Helper 已证明能给本车调出更好的参数。没有找到两者在同一 BM50、同一环路、同一工况和同一评分规则下的对照结果。PID_Helper 作者指出其最佳场景是裸电机速度环和云台，并称小车模式尚待开发。
- 对 BM50 实车，优先保留工作区工具的固件版本/能力检查、板载高频 HLOG、日志完整性门槛、停止确认和增益读回；把候选生成从启发式升级为受约束的黑箱优化，再以独立验证实验决定是否接受。
- 当前 HLOG 自动整定覆盖角速度 PI 与航向 PD。轮速环自动整定尚未通过高频日志路径实现；不能用低频 TEL/ATEL 代替轮速高频数据来做自动增益决策。
- 上次只读检查时，`127.0.0.1:8766` 没有桥接服务监听。因此当时无法直接启动现有工具做实车在线调参。PID_Helper 也没有接入当前固件/桥接协议。

## 工具能力比较

| 项目 | PID_Helper | 工作区现有适配器 |
|---|---|---|
| 已公开的调参方法 | 速度环系统辨识初值；闭环分阶段整定和 PSO；可配置评分权重 | 角速度 PI、航向 PD 的闭环评分与有界启发式候选；另有离线 FOPDT 候选生成 |
| 数据方式 | 串口反馈协议；文章介绍了 target、actual、input、error、P/I/D 等字段 | 通过现有 BM50 WebSocket bridge；角环候选只接受经验证并下载的 MCU HLOG |
| 本车适配判断 | 需要 MCU 实现其协议；文章明确指出小车场景尚未覆盖。其数值不能未经核对就写进本车控制器 | 针对 VGT6 BM50 固件与现有 bridge；受支持的固件版本、控制器形式、单位、周期和限幅都需要匹配 |

## 开源方案调查

### 可参考的搜索算法

1. **贝叶斯优化（BO）**：适合每次实车实验成本高、参数维度较低的场景；根据已测结果选择下一组参数，通常能把有限试验用得更有效。
2. **差分进化（DE）**：适合黑箱、非凸和噪声较大的目标；通常需要更多实车评价，但可作为更稳健的对照搜索器。
3. **CMA-ES**：通用连续黑箱优化器，适合非线性问题；需额外实现 PID 参数边界、失败惩罚、试验安全门和实时硬件接口。

一项移动机器人研究比较了 BO 与 DE，并在差速及全向平台上做了实机旋转实验；其结果指出特定设置下 BO 收敛较快、DE 在所测场景更稳健。该结果适合作为算法方向参考，不能直接外推到 BM50：<https://alibustami.github.io/pid-tuner/>。

### 现成项目参考及限制

- [`bayes_opt_ros2`](https://github.com/VModugno/bayes_opt_ros2)：有 BO 搜索循环和可配置目标函数；公开的快速 PID 配置面向 Crazyflie，主要优化三个 Kp，不能视为本车上已验证的更优工具。
- [`pyPIDTune`](https://github.com/PIDTuningIreland/pyPIDTune)：提供日志、FOPDT 调参、仿真和过程模拟流程，可作为离线辨识/候选/复核工具；公开 README 没有证明它能对本车做闭环在线搜索。
- [`SimpleFOCStudio`](https://docs.simplefoc.com/studio)：支持串口实时监控和手动调参，但主要是可视化调试界面，不是比 PSO/BO 更强的自动搜索器。

目前没有找到一个可据公开、同平台数据断言“全面优于 PID_Helper 和本车适配器”的即插即用工具。对于本车，算法应接入现有合格日志和受控实验，以同一目标函数做 A/B 比较。

## 本车推荐方案

### 短期：保留安全数据链，换掉弱搜索器

1. **先锁定每个环的规格**：环路类型、反馈和设定值单位、PID 形式、控制周期、执行器限幅、级联顺序、固件能力。BM50 当前速度环是增量式控制；角速度内环是 PI，航向外环是测量微分 PD。不同形式的 Ki/Kd 不能直接互换。
2. **固定目标函数和任务工况**：一次优化会话内保持阶跃/正反转轨迹、目标幅值、输出限幅和评分权重一致。性能指标至少保留 IAE、超调、稳态误差、整定时间、饱和比例；安全或质量约束失败的轮次不参与排序。
3. **实现小维度、受约束 BO 为主，DE 为对照**：角速度 PI 搜索 Kp/Ki；航向 PD 搜索 Kp/Kd。先用离线已验证数据/模型做候选范围缩减，再用真实 HLOG 逐轮评价。优化器只能建议本轮候选，不能改变目标、限幅或实验时长。
4. **处理测量噪声和泛化**：每个候选重复测量；在正负方向、多个目标幅值及不同负载/电量状态下复测。把优化用的试验与最后的留出验证分开，防止只对单一阶跃过拟合。
5. **保留门槛和回退**：使用现有 HLOG 完整性、采样密度、模式、时序、饱和及健康检查；每次只在停车后小步写参、ACK 后读回。候选只有通过独立验证才成为本轮最佳参数；结束时恢复并读回已经验证的最佳值。

### 轮速环的前置工作

不要把现有低频 TEL/ATEL 用作轮速自动优化的评分数据。轮速控制周期与角环不同，需要在 MCU 端增加足以覆盖控制瞬态的轮速高频日志，并验证时间戳、覆盖率、无溢出和样本密度。完成日志与评分门槛后，再对单轮或匹配轮组做受限搜索；先验证单轮闭环，再验证麦轮底盘直线、旋转和组合运动表现。

## 如何优化 `pid-tuning` skill

把 skill 的目标从“给出一组 PID 数值”改成“引导一个可复现、可证伪的测量—搜索—验证流程”。建议修改为以下结构：

1. **通用预检**：必须先确认 SISO/MIMO、受控量、执行器量、单位、控制器形式、真实控制周期、输出限制、级联顺序、死区/饱和和安全停机路径。
2. **按数据来源分流**：区分离线 CSV、低速监控遥测和 MCU 高速日志；标注每种数据可用于监控、辨识或增益决策。对指定硬件配置明确不可替代的数据源。
3. **按环路提供 profile**：每个 profile 记录固件版本/CAPS、字段含义、单位换算、控制周期、PID 形式、限幅、可调参数、日志质量门槛及是否允许写回；不匹配时拒绝自动整定。
4. **分离五个阶段**：采集与校验 → 建模/质量报告 → 生成候选 → 离线/仿真复核 → 实车验证与受控写回。模型拟合成功不能替代闭环验证，得分更高也不能越过安全门槛。
5. **候选方法按证据选择**：FOPDT/IMC 等模型法用于适配的稳定自调节单环；高质量闭环试验可使用 BO/DE/CMA-ES；启发式只标为保守初值/有限微调。报告算法假设、搜索区间、重复次数和停止条件。
6. **统一评分及硬约束**：记录目标、综合评分权重、超调/误差/整定时间/饱和等独立指标；对溢出、缺样、时序异常、方向错误、持续饱和、失联或不安全状态直接判失败，不允许插值补齐后参与优化。
7. **强化验证**：比较 incumbent 与 candidate；至少做重复试验、正反向或多幅值验证，并保留未参与优化的 holdout 轨迹。报告均值/离散度和最差工况，而非只展示最好一轮。
8. **写回与恢复**：在线写参必须先确认操作权限和硬件状态；锁定目标/限幅/实验计划；限制每次增益变化；ACK 后读回；失败立即 STOP；只保留实测验证过的最佳值。区分 RAM 写入与 Flash 持久化。
9. **结果格式固定**：每轮保留原始日志、元数据、固件/能力、旧/新参数、命令时间线、评分明细、失败原因及最佳参数选择依据。摘要明确“已验证实机”与“仅仿真/离线”。
10. **显式记录能力缺口**：例如本车当前没有轮速高频 HLOG，因此不得声称已能自动整定轮速环；外部 GUI 工具如 PID_Helper 需要协议适配与 PID 形式核实。

## 可直接继续执行的工作清单

- [ ] 保护当前工作树已有的未提交调参器改动和 `pid-tuning-adapter/runs/` 数据；先检查、不要覆盖或清理。
- [ ] 对照当前实际 `attitude_tuner.py` 与固件 VER/CAPS，确认 HLOG 时间戳分辨率及适配版本；不要从旧交接推断板上版本。
- [ ] 为当前评分目标写出明确定义及合成/历史数据回放基线。
- [ ] 在离线回放或仿真中比较当前启发式、BO 和 DE；记录收敛轮数、最优分数、失败/越界率、对噪声敏感度。
- [ ] 只有离线比较通过后，才在授权的物理测试会话中做受限 A/B；保存原始 HLOG、重复测试和 holdout 验证。
- [ ] 改写 `pid-tuning` skill 的通用流程和 BM50 profile 指针；不要把新算法直接推广到所有 PID 项目。
- [ ] 独立规划轮速环高频日志，不用 TEL/ATEL 补替。

## 实时调用边界

- 现有实车在线入口是 `pid-tuning-adapter/attitude_tuner.py`，经 `ws://127.0.0.1:8766` 的 BM50 bridge 工作；它不是通用 COM 口程序。
- 运行前先做只读 VER/CAPS/健康预检；实际运动必须获得明确的测试授权，确认安全场地和急停，且不与其他客户端争用桥接/硬件。
- PID_Helper 当前没有接入工作区，也没有在当前固件实现其协议。不能直接对当前车辆调用它。
- 上次检查时 8766 无监听。下次运行前重新检查桥接、硬件和板上版本；不能把上次结果当成当前状态。
