# 当前小车工程的 FreeRTOS 移植与性能评估

日期：2026-10-25，Asia/Shanghai。
范围：当前 `vgt6_module_test`，不是仓库中其他示例工程。
验证层级：源码、CubeMX/Keil配置、已有链接结果和官方文档检查。
本轮未修改固件、重新编译、烧录、连接串口或执行实车实验。

## 结论

**可以移植，硬件支持、模块分层和现有DMA/中断驱动均具备基础。**
**合理拆分任务后，可能改善控制周期抖动和MCU内命令处理的最坏等待；不会凭空增加算力，
也不会直接解决蓝牙模块的丢字节、单向回传停止、供电干扰或网页KEEP确认等待。**
当前工程不是把一个大循环搬进默认任务就能获得收益：必须同时处理状态所有权、
时间基准、串口队列和任务栈。移植工作量属于中等，风险主要在调度与并发语义，而非内核启动。

## 当前工程的实际条件

| 项目 | 检查结果 |
|---|---|
| MCU | Keil设备 `STM32F407VGTx`，Cortex-M4F；CubeMX为F407V(E-G)Tx/LQFP100 |
| 时钟 | `.ioc` 配置SYSCLK/HCLK 168MHz |
| 工具链 | Keil MDK，ARMCC 5.06 update 5；必须选择匹配的M4F端口 |
| 当前调度 | `main()`调用`App_Process()`的裸机协作循环，没有接入FreeRTOS |
| 控制 | 基础轮速/IMU调度目标10ms，角环内部累计20ms执行 |
| UART | USART2，115200；RX DMA1 Stream5，TX Stream6；环形接收、发送队列 |
| TOF | I2C1中断式状态机，40ms测量间隔，非长时间轮询实现 |
| 其他工作 | PS2每20ms轮询，电池100ms，OLED整帧250ms，遥测按场景限频 |

主要路径见 `App/Src/app.c`、`Bsp/Src/serial_dma.c`、`Bsp/Src/tof_bus.c`。
现有App/Bsp/Algorithm边界可保留，增加薄的任务调度层即可，不需要先重写所有驱动。

## 资源是否够用

以下为**2026-10-22已有R24链接结果**，不是本轮新构建或运行时测量：

| 资源 | 已有占用/配置 |
|---|---:|
| ROM镜像 | 63340字节，约61.86KiB；Flash容量1MiB |
| 普通SRAM链接区域总容量 | 131072字节，128KiB |
| RW+ZI | 104072字节，约101.63KiB |
| 普通SRAM算术剩余 | 27000字节，约26.37KiB |
| HLOG/WLOG共用的`log_storage` | 90112字节，88KiB；不能重复计算成两份 |
| 已有MSP栈、C库堆保留 | 4096、512字节，已包含在上述链接占用内 |
| CCM | 芯片另有64KiB；当前scatter没有配置此区域 |

小规模4个应用任务加Idle、有限队列，初步可预留约12～20KiB**新增**RAM预算，
但这只是设计估算，不是已编译通过的容量保证。优先使用静态任务和静态队列，
先不启用不需要的软件定时器服务；根据最终map和栈高水位调整。
不要照搬模板配置一个大FreeRTOS heap，再另配一套静态任务栈而重复占用内存。

CCM可考虑放CPU专用的栈或部分数据；不能把UART DMA缓冲放进去。
若任务栈放CCM，也不能把该栈上的局部数组直接作为DMA缓冲。
88KiB日志区不能整体塞进64KiB CCM；最初移植没有必要冒险改变现有日志布局和容量。

## 实际有机会改善的性能

### 1. 控制周期与任务干扰

`App_Process()`按顺序处理串口、TOF、PS2、电池、遥测，再检查控制是否到期，最后刷新显示。
控制释放条件是距离**上次控制完成**至少10ms，并非严格每10ms固定相位释放。
实际控制开始间隔会包含自身执行时间及其他工作的延迟。

- `Bsp/Src/oled.c`逐位调用GPIO发送，每帧1024数据字节及24个命令字节。
  按循环推算，一帧至少约25152次用于逐位传输的`HAL_GPIO_WritePin()`调用，
  尚不含其他控制引脚与文字绘制；这是静态工作量，不能直接换算成已测毫秒数。
- `Bsp/Src/ps2.c`用DWT忙等5us高低电平和16us字节间隔。
  9字节标准帧的显式等待合计约896us；21字节扩展帧约2048us，均未计GPIO和中断开销。
- 电池采样使用`HAL_ADC_PollForConversion(...,5)`；5ms是异常时的等待期限，不是正常采样必耗5ms。
- IMU660RC使用轮询SPI，单次事务超时10ms；重连还会调用含`HAL_Delay()`的初始化。

将显示、电池和通信格式化移到较低优先级，使控制可以抢占它们，有机会降低控制延迟尾部。
但高优先级控制任务自身的IMU等待仍需有界，RTOS不能消除任务内部阻塞。

### 2. MCU端串口命令响应

现在DMA接收完成只入环形缓冲，解析和启动TX仍要等`SerialDma_Process()`。
独立通信任务由中断通知唤醒，可缩短被显示/其他主循环工作推迟的时间。
这是MCU内部的一段延迟优化；无线、USB、浏览器和确认协议造成的延迟仍然存在。

### 3. 不应承诺的收益

- 单核168MHz不会因多任务而增加算术吞吐，调度/同步/FPU上下文还会消耗CPU。
- 轮询SPI、GPIO模拟发送、忙等延时不会因为放进任务就自动变成省CPU的阻塞等待。
- TOF仍受原40ms测量周期约束，遥测无需因RTOS提高频率。
- PID公式、反馈质量、机械误差和带宽不会由内核自动改善。
- 历史网页“等KEEP确认3秒，车端1.5秒保活停车”的问题位于上位机，换MCU调度器不会修正它。
- 现有“仅重启车端模块才能恢复”的故障证据指向模块/接口一侧；RTOS不是针对它的直接修复。

没有本轮CPU占用、各函数耗时与对照实验，不能声称会提升某个百分比、消除全部卡顿或断联。

## 建议的第一版任务划分

| 任务 | 建议职责 | 调度方式 |
|---|---|---|
| ControlTask | 编码器、IMU、角环/速度环、电机输出、运动保护；唯一修改运动状态 | 高优先级，控制周期目标10ms；角环维持20ms，急停事件可提前处理 |
| SensorInputTask | TOF状态机、PS2采集及输入快照 | 有界轮询/中断通知，TOF状态机需较短服务间隔，不能每40ms才调用一次 |
| CommTask | UART接收解析、协议应答、有限发送队列、遥测格式化及日志下载 | 事件驱动，中高优先级，每次处理量有界 |
| UiHousekeepingTask | OLED、电池、低频诊断 | 低优先级，原有100/250ms节拍 |

通信和测距/输入的相对优先级需要按执行时间和最坏到达率验证，不能让通信洪泛饿死TOF任务。
控制周期释放可用合适的周期等待或硬件定时通知；不能把`xTaskDelayUntil()`的到期唤醒
误认为一定准时执行。发生超期时要计数、处理旧目标，避免补跑多个控制步骤重复使用同一反馈。

## 真正需要改造的接口

1. **运动状态只能有一个写入者。** 目前命令、PS2和主循环会在同一上下文顺序调用控制接口。
   多任务后，命令应转换成有时效的消息，由ControlTask执行；应答在执行后返回。
   STOP/DISARM要有独立优先路径，取消旧运动；不能只进入普通队列后就宣称停车成功。
2. **UART保持单一发送者。** 当前`SerialDma_QueueWrite()`没有多生产者互斥。
   多个任务同时直接调用会竞争`tx_head`和队列槽。通过CommTask集中发送，
   保留ACK优先、周期遥测可跳过、有限队列和溢出统计。
3. **快照与日志需要并发边界。** TOF/IMU/编码器结构体复制不是事务；使用短临界区、
   双缓冲或明确的快照发布。日志记录、CLEAR/START/STOP/READ不能并发破坏同一存储区。
4. **重做时间基准的接线。** `timebase.h`把HAL毫秒tick与SysTick倒计数拼成微秒时间戳。
   若HAL改用TIM而RTOS用SysTick，二者相位不再一致；改节拍频率或tickless也会破坏其假设。
   可统一并严格验证同一1kHz基准，或改用独立硬件计时源。不能让HLOG/WLOG时间轴失真。
5. **区分MSP和任务PSP栈。** `stack_usage.c`只检查启动MSP的4096字节，
   不能覆盖RTOS任务栈；必须增加每任务栈高水位、溢出检测、FPU上下文预算和内核断言。
6. **配置异常入口和中断优先级。** 当前SVC/PendSV为空，SysTick仅`HAL_IncTick()`；
   要接入匹配ARMCC5的Cortex-M4F内核端口并核对向量、HAL时基及FPU设置。
   当前PriorityGroup=4、UART/DMA/I2C等优先级5，可以作为核对起点，
   但只有符合`configMAX_SYSCALL_INTERRUPT_PRIORITY`规则的中断才可用FromISR接口。
7. **PS2位时序需要复测。** 多任务抢占可能拉长模拟时钟；不能用整帧关中断来换取稳定，
   否则反而损害控制和UART。必要时调整实现，选硬件外设前再确认引脚和资源。
8. **保持原控制实验语义。** 不因移植擅自提高控制频率、遥测频率或删除保护。
   目前采用完成后等待的周期，新调度若改为固定相位，实际dt也会变化；必须重新验证响应，
   即使增益数值相同也不能直接宣布与原版控制效果等价。

涉及外设、时基、NVIC的修改应回到`.ioc`生成；任务边界与同步写在用户模块中。
首版可保持现有存储位置、原始采样记录格式和串口115200，避免同时更换过多变量。

## 建议的决策与验收

如果近期目标只是解决蓝牙断联，不建议把FreeRTOS作为首要修复。
先继续定位链路损坏，并测量控制耗时；OLED分片/硬件传输、减少轮询和通信限频在裸机下也能改善。
如果后续要并行加入导航、更多传感器及任务，当前结构适合逐步移植，工程收益更明确。

判定“性能改善”至少要在相同遥测负载、控制目标和日志容量下比较：

- 控制开始间隔的分布、最大值及超期次数；单次控制WCET，不能只看平均周期。
- MCU收到命令至解析、执行、ACK入队/实际发送的分段延迟；主机RTT另计。
- 各任务CPU时间、总负载、Idle比例、每任务栈余量和队列峰值。
- UART错误/丢弃/溢出、TOF采样年龄、PS2无效帧、保护停车原因。
- 同条件实车闭环效果与故障注入；WLOG100Hz、HLOG50Hz日志以真实时间戳验收。

建议先建立原版基线，再做可回退的精简RTOS版本；只在同条件对照通过后讨论具体提升幅度。
