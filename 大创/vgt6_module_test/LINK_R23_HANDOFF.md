# R23：蓝牙遥控延迟、排队与链路诊断

2026-10-22。用户要求检查蓝牙遥控大延迟/卡顿/间歇断线，检查修复后烧录；本次授权覆盖固件烧录及停机链路验证，不执行ARM、运动或PID搜索。

## 观察与结论边界

开始时原桥接显示硬件离线。重启同一项目的唯一桥接并记录日志、固定已知WHEELTEC地址后，最初几轮扫描没有看到模块；随后重新发现并连上。不能由“未广播”证明MCU卡死或TOF占满CPU，也不能据此确认断线的硬件原因。没有另启第二个BLE连接；Python venv启动器与其子进程属于同一桥接。

实际板上已为R22（用户/其他窗口已在此前仅编译交付后更新）。停车读回：DISARM、角环mode0/speed0、PS2锁定居中、四轮目标/PWM0、HLOG/WLOG为空且未记录，默认HEAD6/1.25、YAW0.1815/1.8062及四轮增益不变。已有UART FE=4、LINK uart_errors=4，RX溢出/TX丢弃=0；TOF通信errors0，当前常见测量无效raw状态4，仍保持此前用户指定的测距异常不干预速度策略。

原R22+原桥接的停机对照，每组18次PING，间隔150ms（另加完整往返等待），未ARM：

| 串流 | RTT中位数 | P95 | 最大值 |
| --- | --- | --- | --- |
| TEL/TOF均关闭 | 117ms | 172ms | 203ms |
| 只TOF | 109ms | 218ms | 266ms |
| TOF+TEL | 140.5ms | 266ms | 313ms |

54次全部应答，没有新增UART错误或观察到物理断线。因此已有证据支持共享串流增加部分等待，但不支持把大延迟/物理断线全部归因于25Hz的I2C测量。保留25Hz测距，改进发送与控制路径；长时间RF/供电/驱动故障仍需复现后判断。

## 修复

1. 网页原先松键只修改待发向量，正在等待MOVE应答的flush可能迟至应答/超时后才处理STOP。现在松键立即走紧急STOP；MOVE失败也补发STOP。记录motion epoch，晚到的MOVE应答不能重新声明运动所有权或开启KEEP；快速再次按键仍可发送最新向量。JS v35支持R23；没有在实车发送非零运动命令来测试此路径，使用真实JS+模拟延迟应答回归证明。
2. 桥接控制目标入队后超过250ms拒绝执行，同一组连续运动只保留最新排队目标；普通排队命令超过3s也拒绝，STOP/DISARM保持优先取消旧请求。不会自动重试电机指令。
3. 广播给网页客户端的send有100ms上界，慢客户端被移除并关闭，其他观察者与MCU应答不再无限等待它；VOFA drain也有限时。保留原有“先发布原始状态、再完成匹配命令”的顺序。TOF/WLOG实时帧不再逐行刷桥接控制台。物理断连回调立即撤销在线标志、取消旧命令及续发，避免清理GATT期间页面仍报在线。
4. 下位机新增 `SerialDma_WriteTelemetry`：完整收到命令后的80ms内让出可选周期遥测；UART已有任何待发/正在发帧时跳过过时遥测，不累计待发实时画面。单次查询回复、ACK、HLOG/WLOG下载仍走原可靠FIFO。已经开始发送的完整串口帧不截断，无法消除其固有发送时长。
5. TOF本地预算33ms/间隔40ms/ready轮询2ms、100mm前进停止和200mm前进上限40RPM保持R22。名义距离显示仍为单流10Hz、与状态同开5Hz；繁忙时主动跳过部分显示帧，板载测量和前进保护持续运行。
6. 只读 `LINKQ,pending_frames,pending_bytes,telemetry_skipped,command_age_ms` 监测TX队列；主动跳过周期遥测单独计数，不混进UART错误或普通TX丢弃，也不会丢弃RAM日志样本。CAPS增加UART_QOS，VER/OLED/读回标记为R23。角环和轮速精确白名单加入R23，HLOG/WLOG方程、格式、采样校验未放宽。
