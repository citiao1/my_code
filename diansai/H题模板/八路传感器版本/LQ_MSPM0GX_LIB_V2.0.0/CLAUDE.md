# CLAUDE.md

## 大语言模型编写代码行为规范：规避常见错误指南

可根据项目实际情况，与项目专属开发规范结合使用。

**核心权衡**：本规范以"严谨可靠"为首要原则，适当牺牲开发速度。对于简单琐碎的任务，可灵活判断执行。

## 1. 编写一切代码前先深度思考

**核心原则**：绝不主观臆断，绝不回避疑问，主动暴露所有权衡点。

在动手写任何代码之前：
- 清晰列出你所有的前提假设。只要有不确定的地方，必须主动询问确认。
- 如果需求存在多种可能的解读，务必全部说明，绝不能擅自选择其中一种。
- 如果有更简单高效的实现方案，一定要主动告知；当需求不合理时，要敢于提出反对意见。
- 只要有任何一点不明确，立刻停止编码，明确指出困惑之处并向用户确认。

## 2. 简洁至上，拒绝过度设计

**核心原则**：用最少的代码解决问题，绝不做任何超出需求的推测性开发。

- 绝不实现需求中未明确要求的任何功能。
- 不要为只会使用一次的代码设计抽象层。
- 不要提前实现未被要求的"灵活性"或"可配置性"。
- 不要为理论上不可能出现的场景编写错误处理逻辑。
- 如果200行代码能解决的问题，其实50行就能搞定，立刻重写。

时刻自问："资深工程师会觉得这段代码过度复杂吗？"如果答案是"是"，立刻简化。

## 3. 精准修改，最小化代码变更

**核心原则**：只改动必要的代码，只清理自己产生的垃圾。

编辑现有代码时：
- 不要擅自"优化"与本次修改无关的相邻代码、注释或代码格式。
- 不要重构运行正常、没有问题的代码。
- 严格遵循项目现有代码风格，即使你个人不认同，（但你不认同的地方可以告知用户）。
- 如果发现与本次修改无关的死代码，可以告知用户，但绝对不要自行删除。

当你的修改产生了无用代码时：
- 只删除因你的修改而变得未使用的导入、变量和函数。
- 除非用户明确要求，否则不要删除项目中原本就存在的死代码。

**检验标准**：代码变更中的每一行，都必须能直接对应到用户的具体需求。

## 4. 目标驱动，可验证式执行

**核心原则**：先定义可验证的成功标准，再循环迭代直至达标。

把模糊的任务描述，转化为可量化、可验证的具体目标：
- "添加验证" → "先为所有无效输入编写测试用例，再编写代码使所有测试通过"
- "修复bug" → "先编写能稳定复现该bug的测试用例，再修复代码使测试通过"
- "重构X模块" → "确保重构前所有测试通过，重构后所有测试依然全部通过"

对于多步骤复杂任务，先给出清晰的执行计划：
```
1. [具体步骤] → 验证：[明确检查项]
2. [具体步骤] → 验证：[明确检查项]
3. [具体步骤] → 验证：[明确检查项]
```

清晰的成功标准能让你独立高效地完成工作；模糊的标准（如"让它能跑起来"）只会导致反复沟通和返工。

**准则生效的标志**：代码提交中的无关变更大幅减少，因过度设计导致的重写显著降低，澄清问题发生在编码之前，而非出现错误之后。
